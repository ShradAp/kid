# Codex в Windows: защита, запуск и проверки

27 октября 2026. Официальный Codex App Server 0.164.0-alpha.11.1 запускается
непосредственно в Windows. Docker и Proxifier для Codex больше не нужны.
Обычная точка входа остаётся WEB_UI.pyw; интерфейс приложения сохранён.

## Граница защиты

Соединения самого Codex с сервисом: вход, обновление токенов, модели, лимиты,
генерация и переподключения — проходят через настроенный прокси. Обычные
Windows-команды, браузеры и инструменты kid могут использовать обычную сеть.
Это уточнённое пользователем требование: запрет не распространяется на весь ПК.
Произвольная разрешённая команда технически способна запустить другой сетевой
клиент; она не становится частью защищённого транспорта Codex.

## Принудительная маршрутизация

Встроенная Windows Filtering Platform содержит девять постоянных фильтров:
по три для отдельных codex.exe, codex-code-mode-host.exe и network-probe.exe
в каталоге данных kid/codex_native. Каждый executable может открывать TCP
только к 127.0.0.1:47693. Остальные IPv4 и все IPv6-соединения запрещены.
Ограничения не затрагивают системный Python, VS Code, другие Codex или браузеры.
Закрытие приложения и установщика не удаляет запреты.

На этом порту находится локальный посредник kid. Профили используют разные
случайные токены. Посредник открывает внешний сокет только к числовому адресу
прокси через существующий connect_via_proxy. У него нет direct fallback,
автоматического выбора системного прокси и локального DNS для целевого домена.
Домены назначения передаются удалённому прокси через CONNECT/SOCKS5h.
Посредник допускает HTTPS OpenAI/ChatGPT и проверочный ipify; произвольный
сетевой маршрут через него не предоставляется.

Сначала проверяются SHA-256 компонентов и реальные объекты WFP, затем четыре
сетевых проверки, и лишь потом запускается Codex. Проверки используют
контролируемые локальные TCP/UDP-приёмники IPv4/IPv6. У каждого пути сначала
проходит положительный контроль обычным процессом. Защищённый TCP получает
WSAEACCES; защищённые UDP-пакеты не доходят до работающего приёмника.
Успех sendto сам по себе не считается прохождением пакета: Windows может
отбросить UDP после успешного возврата sendto. Внешних пробных пакетов нет.

Codex и его потомки находятся в отдельном kill-on-close Windows Job.
Остановка транспорта закрывает также дочерние компоненты. WFP дополнительно
проверяется во время работы. Ошибка подключения посредника завершает профиль;
прямого повтора нет. Нормальное закрытие TLS-туннеля не удаляет ограничения:
повторное соединение снова может идти только через посредник и тот же прокси.

Установка выполняется атомарно с однократным UAC. Обычный kid читает только
собственные объекты политики; общие права BFE и чужие правила не меняются.
Windows автоматически добавляет флаг INDEXED и может нормализовать вес подслоя;
проверка допускает эти служебные изменения, но отвергает DISABLED, изменение
действий, условий, адреса, порта, идентификатора приложения и весов фильтров.

## Инструменты и реальные действия

Локальный stdio MCP предоставляет общий набор инструментов kid. Входящий HTTP
канал MCP к backend — только loopback, с отдельным случайным Bearer-токеном,
ограничением размера и запретом Origin. Протокол MCP использует UTF-8 и на Windows.
MCP обязателен: ошибка его запуска не превращается в молчаливую работу без инструментов.

В закреплённой версии маршрутизация инструментов требует code_mode_host.
Официальный вспомогательный executable включён только после установки для него
такой же защиты WFP. Браузерные функции, автоматическая установка плагинов,
встроенный shell и отдельный code_mode отключены. App Server работает read-only;
действия на ПК выполняет отдельный исполнитель kid после его собственных
подтверждений. MCP default_tools_approval_mode=approve передаёт вызов этому
исполнителю, не отменяя подтверждения kid.

windows_command выполняет PowerShell или CMD в настоящей Windows-папке.
Команда отображается до подтверждения; опция авторазрешения сохраняется в профиле.
Есть отмена, лимит времени 120 секунд и вывода 512 КиБ. Дерево команды находится
в отдельном Job; отмена завершает потомков. Фоновые потомки команды также
завершаются при закрытии этого Job.

windows_write_file создаёт новый TXT/MD/CSV/JSON/DOCX на настоящем рабочем столе
(включая OneDrive) или в выбранном проекте, не перезаписывает существующие файлы
и требует подтверждения. Произвольные операции доступны через подтверждаемые
Windows-команды. Просмотр текста и Git diff используют настоящую папку проекта.
Внешние Git helpers, textconv, fsmonitor и lazy fetch для diff выключены.

Поиск Codex включает встроенный поиск и скрывает поисковые инструменты kid.
Поиск kid отключает встроенный поиск и предоставляет поиск, чтение и GitHub-анализ
kid. Исследовательский контроллер получает callback model_completion App Server:
скрытой зависимости от платного чат-API нет. Произвольные сетевые команды Windows
разрешены отдельно и не гарантируют использование выбранного поискового движка.
Чтение сайта возвращает текст и источник; встроенного браузера нет.

## Вход, история и запуск

После первого входа используется сохранённый аккаунт. Для native runtime выделен
native_server внутри каталога профиля: Linux SQLite нельзя одновременно открывать
как Windows-состояние. Сохранённая авторизация копируется однократно; прежние
файлы не меняются. Новые native-диалоги продолжаются после перезапуска.
История kid и журнал выполненных действий сохраняются. При смене старого контекста
в новый поток передаётся ограниченная предыдущая переписка как цитата с запретом
повторять завершённые действия. Неопределённый исход старого хода не переигрывается.

При подключении через обычный интерфейс kid сам скачивает официальный Windows
пакет через прокси, проверяет SHA-512 архива и SHA-256 файлов, при необходимости
вызывает установку WFP с UAC. Вручную скачивать Codex или настраивать firewall не нужно.
Обычный запуск после подготовки не требует администратора. Отсутствие прокси,
отмена UAC, конфликт порта, повреждение компонентов или правил блокируют Codex.
API-профили и Document Studio не переводятся на новый движок.

## Проверки

Выполнены реальные проверки WFP и четырёх транспортов; сохранённого входа,
получения моделей и лимитов; генерации, отмены, продолжения после перезапуска
и отсутствия повторного исполнения; модельного вызова локальных инструментов
с PowerShell-командой и созданием файла в временной Windows-папке.

Проверены настоящим native-клиентом недоступный прокси, ответ 407 и разрыв TLS
на контролируемых локальных прокси. Отдельный обычный процесс подтвердил наличие
прямого интернета TCP к не-OpenAI адресу; прямых запросов OpenAI не выполнялось.
Полный тестовый набор и браузерная проверка интерфейса запускаются отдельно;
актуальные результаты последней проверки фиксируются в ответе по задаче.

Итоговая проверка: 214 Python-тестов прошли; production-сборка Next.js прошла;
браузерный smoke прошёл. Настоящий запуск WEB_UI.pyw подтвердил через локальный
Next.js→Python API состояния authenticated, verified и runtime=windows-native.

## Ограничения

Механизм рассчитан на штатную Windows/BFE. Администратор может намеренно удалить
правила или заменить программу; защиты от скомпрометированной ОС не обещаем.
Закреплённая версия App Server экспериментальная. Автоматической подмены версии
нет: обновление требует повторной проверки протокола, компонентов и маршрутов.
Git нужен только для diff, VS Code — только для кнопки открытия внешнего редактора.
Старые Docker-диагностики оставлены как исторические скрипты, но runtime приложения
их не выбирает и при сбое на Docker либо прямой Codex не переключается.

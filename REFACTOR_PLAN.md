Состояние, которому нужен ровно один владелец:

- `LIVE_THINKING`, `LIVE_REASONING`, `LIVE_REPLY`, `CANCEL_EVENTS`: связаны с одним ходом и доступны генерации, progress, stop и shutdown. Нельзя копировать словари или хранить отдельный набор для каждого handler.
- `sessions_memory`, `sessions_meta_memory`, `DELETED_SESSIONS`: загрузка, отправка и удаление диалога; удалённый во время генерации чат не должен воскресать. `CODEX_SERVICE.history_reader` сейчас замыкает этот же кэш.
- `studio_sessions_memory`, `studio_sessions_meta_memory`, `DELETED_STUDIO_SESSIONS` и ключи studio-профилей отделены от основной истории. `STUDIO_DOCS` и нерекурсивный `STUDIO_LOCK` относятся к рабочему документу; фронтенд использует общий ключ `document-studio`. Не превращать это в отдельный документ на каждый чат.
- `FILE_ACCESS`: одно множество разрешённых пользователем файлов; используется загрузкой, chat, preview, download и Codex-вложениями. Перенос не должен выдавать разрешение произвольным путям.
- `CODEX_SERVICE`, `CODEX_LIMITS`, `CODE_WORKSPACES`: создаются один раз. Сеансы, очередь подтверждений, журнал и отмена общие для маршрутов; сохранение общего прокси закрывает старые сеансы и запускает защищённое переподключение.
- Баланс: последний успешный результат, TTL-кэш, lock и состояние фонового обновления — один блок, не разносить их по маршрутам и клиенту.
- Жизненный цикл: сервер, frontend process, BRIDGE_STARTED, SHUTTING_DOWN, locks, window-ready и окно. Порядок закрытия и однократность очистки являются поведением.
- `BASE_DIR`, пути UI и defaults вычисляются относительно корня проекта; перенос модуля меняет смысл `__file__`. Источник корневого пути оставить в [app_paths.py](app_paths.py), не менять размещение данных.

## 4. Проверенные цепочки сценариев и скрытые связи

1. **Запуск/закрытие.** Проверка зависимостей → mutex/активация предыдущего окна → Job → backend → проверка занятости frontend-порта → Next.js → фоновый прогрев памяти (не для Codex) и защищённое подключение активного Codex-профиля → HTTP-прогрев → окно → трей/хоткей. Закрытие отменяет ход, закрывает service/server/network agent/Next.js и освобождает дерево процессов. Не запускать main из теста в исходном каталоге: это может активировать рабочее окно.
2. **API.** UI фиксирует session/persona/operation, загружает файлы и опрашивает progress. Backend сначала выбирает engine; только API-ветка извлекает обычные вложения, выбирает профиль, обновляет метаданные/промпт/историю, выбирает tools, выполняет SSE/tool-цикл и сохраняет ответ. Отмена, ошибки провайдера, fallback-ответ и обработка content-policy уже имеют особую семантику; не «улучшать» её при переносе.
3. **Codex.** Роутинг происходит до API, памяти, research и баланса. Вложения проходят отдельную проверку. ProfileSession использует привязки контекста/операций, не переигрывает выполненные действия. Настройка runtime/хешей/WFP/контрольных транспортов предшествует App Server; broker подключает только прокси. Ошибка не переводит запрос в API.
4. **Инструменты.** Имена из `TOOLS_SCHEMA`/`WORD_TOOLS_SCHEMA` → tool_gating/MCP schema → диспетчер по строковому имени/словарь handlers. `_WORD_TOOL_NAMES` строится из схемы через getattr. `native_codex.tools` и legacy worker вызывают память через getattr. `ProfileSession.tool_bridge` сверяет активный ход, search mode, отмену и журнал; host callback находит ход по тому же cancel Event. OS-approve/reject различает ID с префиксом `codex_` и обычную очередь win_tools.
5. **Хранение.** Конфигурация/история сохраняются через config_manager; в desktop есть кэши и адаптеры. Заметки используют RLock, fsync, replace и уникальный временный файл; ошибка записи не должна превращаться в успех. UI сохраняет очередь изменений заметок и локальный fallback, защищает новый ответ от запоздавшего init. Legacy-миграции/purge и имена файлов сохраняются.
6. **Профили/настройки.** `/api/init` строит UI-представление с пустыми полями секретов и has-флагами. `retained_secret` отличает пустое значение от явного удаления ключа. Студийные профили — тот же config, но отдельный флаг и active/meta keys. Смена общих настроек прокси закрывает Codex и отдельно обновляет network_agent.
7. **Документы.** Upload/выбор → FILE_ACCESS → разбор или рабочий документ studio → analyze/state/preview/apply/preset-save/compile → services.word_automation → разрешённые download/generated-ссылки. Word-инструменты и ручная панель используют одну логику документа. API- и Codex-вложения имеют разные действующие контракты; не объединять их в один «универсальный» обработчик.
8. **Сеть.** Codex transport не равен public guest transport. Обычное чтение может иметь proxy/direct fallback; SSRF/лимиты проверяются отдельно. Локальный UI-прокси к Python не является внешним прокси. Оценщик поиска для Codex использует model_completion App Server, а не платный API-клиент.

- [WEB_UI.pyw](WEB_UI.pyw), [test_desktop_launch.py](tests/test_desktop_launch.py), [test_security.py](tests/test_security.py), [test_storage_stability.py](tests/test_storage_stability.py) импортируют desktop_app и подменяют его функции/компоненты. Старый импорт функции без сохранения механизма подмены не обеспечит совместимость.
- UI-маршруты вызываются строковыми fetch-адресами из страницы, диалогов, панелей и [studio-data.ts](UI/src/lib/studio-data.ts); file URLs сохраняются в истории. Сохранить status codes, поля, query string и Content-Disposition, а не только JSON успешного chat.

## 7. Как сохранять совместимость

- Пути данных остаются в app_paths/config_manager: KID_CONFIG_DIR, history/studio_history, notes.json, data, generated_files, presets, backups, config snapshots. Не менять sanitization ID, миграцию или старые download-ссылки.
- Обёртки старых desktop_app-функций разрешены временно для реальных импортов/тестов/скриптов. Делегирование идёт к единственной реализации и тому же объекту состояния. Простая копия ссылки на dict/function не подходит для присваивания новой зависимости в старом модуле; вызывающие стороны переводятся на явную dependency boundary в том же шаге либо поддерживается узкая обёртка.
- Public exports api_client, memory.user_profile и services.word_automation сохраняются. Не создавать две реализации схемы, notes IO, документа или генерации.
- Сохраняются API-адреса, методы, лимиты, status codes, payload/поля ошибок, SSE callback semantics, поле display/attachments, Codex operation/activity/images, secret retention и все два режима поиска Codex/kid.
- Не переносить process_cleanup так, чтобы изменилось имя mutex, вычисляемое из пути этого модуля. Не менять Job ownership, WFP, startup gates, environment allowlist, отключённые flags и required MCP.
- Перед переносом кода, участвующего в runtime_sources/подготовке, проверять импорт в отдельном процессе и состав упаковки. Не пересоздавать защищённый runtime и не обновлять закреплённые компоненты только из-за структурной правки.

## 8. Обнаруженные расхождения: требуют отдельного решения, не входят в структурные исправления

### 8.1. Память: желаемый принцип отличается от API-кода

Исходное требование пользователя: модель обращается к памяти по необходимости. При обследовании API-ветка [desktop_app.py](desktop_app.py) около исходной строки 3442 вызывала `build_memory_context(user_prompt)` до генерации и добавляла факты в system prompt (кроме trivial/smalltalk); Codex использовал инструменты. После remember/manage_memory блок обновлялся ещё раз. [build_memory_context](memory/user_profile.py) реально выполняет retrieval и форматирование; это не пустая заглушка. После переноса прежняя API-логика находится в [application/chat_api.py](application/chat_api.py).

Не утверждать, что инструментальный принцип уже соблюдён во всех движках. Не добавлять автоматическую подстановку в Codex. Удаление существующей автоматической подстановки API изменит поведение и не должно маскироваться переносом. **До переноса этого участка нужно согласовать: сохраняем наблюдаемую API-семантику в структурном шаге или отдельно меняем API-память на обращение по инициативе модели.** Остальные переносы независимы.

Решение по 8.1 получено: пользователь явно подтвердил сохранение существующей автоматической подстановки памяти в API и инструментального доступа в Codex. Перенос выполнен в [application/chat_api.py](application/chat_api.py) и [application/chat_tools.py](application/chat_tools.py); автоматическая подстановка и оба memory handlers сверены с исходной рабочей версией по AST с заменой только имён зависимостей. Политика памяти не менялась.

### 8.2. OpenAI через универсальный API-клиент

Защищённая ветка Codex проходит через broker/WFP и не имеет API fallback. Однако [api_client.py](api_client.py) использует `Session.trust_env=False` и допускает явные direct-попытки в обычном и SSE-вызове, а base_url настраиваемый. В [desktop_app.py](desktop_app.py) также есть `_NO_PROXY_OPENER` для API models/balance. Следовательно, статический анализ не позволяет гарантировать правило «любой OpenAI-трафик только через прокси» для произвольного API-профиля с прямым адресом OpenAI. Личные настройки не читались, реального нарушения для профиля пользователя не установлено.

**Не обращаться к реальным Codex/OpenAI endpoints в проверках этапа 1. Не ослаблять действующие gates.** Для API-профиля с OpenAI URL нужен отдельный согласованный пункт: запрет такого endpoint до наличия защищённого маршрута либо специальный принудительный маршрут для него. Это изменение поведения/политики, не структурный перенос и не объединение с обычной сетью. Рефакторинг независимых частей может продолжаться; сетевой контракт этой ветки не менять молча.
